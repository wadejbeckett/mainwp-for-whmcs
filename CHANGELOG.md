# Changelog

## 0.6.0 (16 November 2026)

- The dashboard's client list is read 100 rows at a time (the site list stays at 20, because a site's row carries its plugins and themes). Setting up care for a client now takes far fewer calls on a dashboard with many clients (9 in place of 33 with 600 clients). Of each row the module keeps only what it uses, so a long site list is never held whole in memory.
- When a daily check finds more than it can keep (100 lines at most), the digest says how many more there are and that the module's page has the same lines and no more; it no longer calls the page the whole list.
- The README says which client-area themes the client's panel and connect page are written for (Nexus and Twenty-One; plainer spacing under Six), that the module is in English only, and what was measured on a dashboard with hundreds of clients and sites.
- Clients read your care add-on's own name, as you set it in WHMCS, on their panel and on the connect page. The module stores no service name of its own. Where it cannot tell which add-on is meant, it uses the name of your only care add-on, and otherwise the words "Website Care".
- Nothing a client reads names MainWP or MainWP's plugin: the client reads that "a plugin that lets us look after your site" is installed. With MainWP's White Label extension the plugin carries your brand on the client's site; without it, the site lists it as "MainWP Child".
- The care account the module makes on a client's site still has a login beginning "wpcare", so existing care accounts are still recognised.
- A care add-on must sit on a hosting service that has a domain. One that has none is not provisioned: the log and the daily digest tell staff why, and the client reads that the service has no domain.
- When a customer's email address already belongs to a client on the dashboard, the site is filed under that dashboard client when exactly one has that address (letter case ignored) and its note names no other WHMCS client. Its note is not changed, and the log says so. Otherwise the failure says what staff can do.
- One MainWP dashboard serves one WHMCS; the README now says so.
- The Test Client ID setting is gone. In dry run no client sees the connect prompt or the connect page: dry run is for staff. Live mode can be saved only with an API key and a Care Account Email.
- The client's connect page asks for the site's address once, in one form, with both ways to connect below it. A reason that is about your own set-up (no Care Account Email, a System URL that is not https://) is no longer shown to the client.
- A second care add-on of the same client, for a site that another of their care add-ons already covers, is refused on the client's connect page and on the staff Connect Site form with a plain sentence, also after a redirect; the daily check reports it and lets go of the login or key a failed connect kept for retries.
- The application password a client approves, and the care account made on their site, are named after your care add-on. A client's site is called with the User-Agent "Website Care": if a firewall on a site lets the module in by its User-Agent, change the rule.
- "Last synchronised" on the client's panel and page is shown in WHMCS's own date format.
- When the dashboard does not answer as MainWP's REST API, or refuses the API key, the message to staff now also names the two commonest causes: permalinks set to Plain, and a web server that does not pass the Authorization header on to WordPress.
- Live mode also needs the MainWP Dashboard URL. An install that was Live before can still save its other settings without a Care Account Email.
- Pressing Enter after typing a login on the connect page connects with that login. Two care add-ons that both still wait no longer keep each other from the same address. The page of an add-on that is paid and not yet provisioned says what its panel says.
- Deactivating says what is kept (the tables, which hold the care accounts' logins, encrypted) and that WHMCS removes the module's settings. The staff Connect Site form has lost its long help text, and the staff panel says why an add-on with no domain is not provisioned.
- Each module folder carries a `whmcs.json`. The tests and the comments in the code no longer refer to one host's own install.
- The README is rewritten for a host installing the module for the first time, and states plainly what stays behind when care ends: the care administrator account and MainWP's plugin (which MainWP switches off) on the client's site, and the dashboard client on the dashboard. The full behaviour is in `docs/reference.md`, now in the release zip.
- Activating the module over tables kept from an earlier version brings them up to date, as an upgrade does. The release zip is the same on every machine, and a release is refused when its change log entry has no date.

## 0.5.0 (16 November 2026)

- A site or dashboard that sends a very large answer no longer stops the daily check: the module reads at most 2 MB of any answer and treats a larger one as a failed request whose reason says the answer was too large.
- Changing the dashboard address to another host now asks for the API key again, so the saved key is never sent to another host. Live mode cannot be saved without an API key.
- A client site that is slow to answer no longer stops the daily check's mends and retries for every other site: it is reported on its own line as a site that did not answer in time.
- A connected site that the last daily check found disconnected, and could not mend, now reads Disconnected on the staff panel as on the Sites tab; the client reads "We cannot reach your site at the moment." instead of "Your site is connected and cared for.". The staff panel also shows what the last daily check found for every care add-on, under Issue. In the digest the states "Not provisioned" and "On the dashboard only" now start with a capital.
- While the add-on module is deactivated, Create, Suspend, Unsuspend and Terminate answer "The add-on module MainWP for WHMCS is not active.", so WHMCS keeps the add-on's status (and, for its own automated runs, holds the command in its Module Queue), instead of answering success with nothing done.
- Which product add-ons are care is set in one place: a product add-on is a care add-on when its Module Settings in WHMCS name MainWP for WHMCS. The tick boxes on the Settings tab are gone; the tab lists the care add-ons by name, each linked to its page in WHMCS. An add-on that was ticked but does not name the module no longer counts as care until the module is chosen on it. The daily check's line for a care site whose add-on no longer counts says "or its Module Settings no longer name MainWP for WHMCS".
- No product add-on is a care add-on by default: activation stores none. The old saved list is left where it is and no longer read.
- The daily check reports a site on the dashboard that no care add-on covers only when it is under a dashboard client the module made (its note says "WHMCS client" and the number); sites under clients made by hand on the dashboard are left out.
- A site address typed with http:// is no longer retried, the login typed for it is not kept, and the client is not told it will be tried again.
- After an upgrade by unzip the module's admin pages and client panel show the new version's templates even when the files keep older dates: the compiled templates carry the module's version. The README's upgrade steps now also say to empty WHMCS's template cache.
- The requirements are now WHMCS 9.1 (tested), PHP 8.2 to 8.4 and MainWP Dashboard 6.4 (tested). For development: the composer lock is refreshed, the integration test runs on MySQL 8 as well as MariaDB and leaves no tables behind when its set-up fails, and CI runs PHP 8.2, 8.3 and 8.4 and the integration tests against MariaDB.
- Nothing a client reads names MainWP any more. A reason whose words name MainWP (the dashboard's own words about a site, or a reason stored by an earlier version) reads "Your site could not be connected." to the client; staff read the words in the module log, on the staff panel's Last Connect Attempt line and in the digest. What the dashboard says about the login itself is still told, and the client's own site address never hides a reason. An error of the module itself reads as a fault on our side, whatever its words. The return address that WordPress prints on the client's approval screen, and the notes in the address bar, are named `care_return`, `care_rejected`, `care_result`, `care_note` and `care_key`; an address with the earlier names is still read, so an approval started under an earlier version comes back and is taken.
- Sites and clients are read to the end of the dashboard's lists. MainWP's clients list calls each page's own rows the total, so a dashboard with more than one page of clients lost the rest, and a customer whose dashboard client was among them could not be provisioned ("Client email exists"). The lists are now read 20 rows at a time until a page brings nothing new.
- No upgrade step: the update is files only.

Next, connect your site so that we can start looking after it.".

## 0.4.1 (16 November 2026)

- The daily digest names each care add-on that is Active in WHMCS and set to free (the billing cycle "Free Account", or a recurring amount of 0.00): one line each, after the failed commands, with the care site's state (or "Active in WHMCS" when it has no care site or a removed one) and the words "set to free in WHMCS". The add-on is provisioned and cared for as before. Check Now and Dry Run list the line too, and the Sites tab shows it beside the site's other finding. No setting.
- The digest lists every open Module Queue row of the module for a care add-on, whatever its action word, except a Create. A Suspend, Unsuspend or Terminate stored in any letter case is named by WHMCS's button word; any other command by the word WHMCS stored (its first 40 characters). A failed Create stays out: the daily check provisions the add-on once it is billed.
- Three sentences of the 0.4.0 notes, and one in the README, said more than the module does, and are corrected: when a second cron run on one day logs that a digest was already sent, when a default port is accepted, and when a provision refused by the client lock is tried again.
- No upgrade step: the update is files only.

## 0.4.0 (16 November 2026)

- The daily check's email is the daily digest. Never more than one goes out on one calendar day: a second cron run that day sends nothing; when it had something to send, the log says "not sent: one was already sent today", and otherwise it writes no digest row. A digest that could not be sent uses up no day, and what it would have told is still new for the next run.
- The digest lists failed Suspend, Unsuspend and Terminate commands of care add-ons from WHMCS's Module Queue, first under New and first under Still open, with the error and how often it was tried. The module reads the Module Queue and never changes it. Check Now and Dry Run list them too, and the Sites tab shows them beside the site's other finding.
- The "Daily Report" tick box on the Settings tab is now the "Daily Digest" drop-down: Off, When something is new, or Every day. A ticked box reads as When something is new and an unticked one as Off, so nobody's email changes. On Every day a quiet night sends "MainWP for WHMCS: nothing to report", and a night with only old lines says how many are still open. No upgrade step.
- When a failed command is listed, the digest ends with a link to WHMCS's Module Queue, to retry it there (without a System URL it names Utilities > Module Queue in words).
- In the digest each paragraph and each line stands on its own line, and each line names its add-on.
- An invoice in Payment Pending or Collections now counts as unpaid, as Unpaid does, so care is no longer set up before the money arrives. A Draft invoice does not count: the client can neither see nor pay it.
- Two requests for one new client at the same moment no longer each create the client on the dashboard: provisioning finds or creates the dashboard client one request at a time for each WHMCS client. A request that waits more than ten seconds fails; the add-on is tried again at the next daily check while it has no open invoice, and otherwise when its invoice is paid.
- The README now says to choose "Automatically setup the addon as soon as an order is placed" on the care product add-on's Module Settings, not "when you manually accept a pending order". WHMCS then calls the module at checkout, and care is set up when the invoice is paid, with no staff click. On an install that keeps manual acceptance, care waits for a staff click on every order: change the setting on the product add-on.
- The module's log no longer names a client site's administrators when MainWP lists them: it says how many ("3 administrators").
- An address typed with its scheme and its default port (`https://example.com:443`, `http://example.com:80`) is accepted as the address without it, and a site that reports its address so is the same site. Without the scheme (`example.com:443`) it is still refused, as is another port.

## 0.3.0 (15 November 2026)

- MainWP for WHMCS now includes a WHMCS provisioning module (`modules/servers/mainwp`), selected on the care product add-on's Module Settings (Addon Type: Independent Product). WHMCS's own automation calls it: CreateAccount provisions the care site when the add-on is set up and billed, SuspendAccount suspends the site when WHMCS suspends the add-on (the cron's Overdue Suspensions or staff), UnsuspendAccount resumes it when the overdue invoice is paid, TerminateAccount removes it. Before this, an add-on suspended by the cron for an overdue invoice was not heard by the module, and the site stayed cared for. A suspend, unsuspend or terminate that the dashboard or a busy add-on stops answers WHMCS with the reason, so WHMCS keeps the add-on's status and holds the command in its Module Queue for Retry; a create that does not reach the dashboard is logged and the add-on is set up all the same, and the daily check provisions its care site once the dashboard answers. The hooks stay for what WHMCS changes without calling a module (a status set by hand or through the API, the hosting service's own module commands, a deleted add-on, the daily check). In dry run WHMCS's status changes while nothing is sent; switching to Live does not apply those changes afterwards. No schema change; no server record is needed.
- The client's care panel moves to the sidebar of the service's page in the client area (`ClientAreaPrimarySidebar`), between the service's Overview and its Actions when the sidebar carries WHMCS's stock panels, and is no longer returned from `ClientAreaProductDetailsOutput`. The theme prints that hook's output only in WHMCS's default service overview, so a service whose server module shows its own overview (Plesk's, for one) showed no panel. Every theme draws the sidebar, whatever the service's server module. The panel carries an icon, as WHMCS's own panels do.
- A typed address must be the site's own. Before an approval is started or a login is sent, the site's public REST index is read, and when the typed address is on the host of an address WordPress there reports as its own but is neither of them (the scheme, the host's case, a leading "www." and a trailing slash do not count), nothing is started, sent or stored, and the client is told the address to enter instead; the staff Connect Site form refuses the same way, with a log row. Before this, a folder with no WordPress of its own could be accepted, because WordPress sends the main site's REST link on every path. A WordPress in a folder, whose index reports the folder, still connects; an index that names no address, or cannot be read, changes nothing.
- After a typed address is refused, the client's page shows the stored address as the site's heading and offers the ways a fresh load would; only the field the address was typed in keeps it, to be corrected.
- The client's page is headed "Connect your WordPress site" only while the site waits to be connected; otherwise "Your WordPress site".
- A client who may see a care add-on that is not Active on an Active hosting service (unpaid, suspended) no longer reads "This page is not available" on its page: it shows the site's address and the sentence of the client's panel, with no form, and a "View your invoices" link when the add-on has an unpaid invoice.
- Suspended care says why when the module knows: "Care is suspended until its invoice is paid." where the add-on itself is suspended and has an unpaid invoice, otherwise "Care is suspended."; a site suspended on the dashboard reads "Care is suspended: updates and health checks have stopped.".
- The dashboard call that points a site at an administrator is logged as "dashboard: switch administrator": its old label was longer than the log's action column and was stored cut short.
- On the staff pages the records line of a list is laid out as WHMCS lays out its own, and the last connect attempt in the staff panel is dated in the admin's own date format.

## 0.2.0 (11 November 2026)

- "Care Account Email" replaces "Care Account Email Domain" on the Settings tab: one email address, given to the care account on every site. It is checked as an email address and stored in lower case. The upgrade from 0.1.0 turns a domain that was set into `wordpress@<that domain>` and deletes the old setting, and is safe to run twice.
- A care site records its other administrators (a new column, `mod_mainwp_sites.other_admins`, added by the upgrade from 0.1.0), by login name only.
- The username-and-password way makes the care account too. Once the dashboard has connected the site as the administrator typed, it makes the care account on the site, is pointed at it and syncs; the care account becomes the stored login and the login typed is deleted. A site that refuses the account gets one more try with a new login and the address plus-tagged with it. When the care account cannot be made, the dashboard is pointed back at the administrator typed, the site is Connected all the same, the login typed is deleted, and the log says why.
- A care login typed in the Connect Site form (a host that made the care account and switched MainWP Child on on the server) is given to the dashboard without a login to the site; only when the dashboard refuses does the module log in with it, switch MainWP Child on and ask again. No other account is made.
- On the approve route, a site where another account holds the Care Account Email makes the care account with the address plus-tagged with its login.
- A deleted care account no longer drops the site. Mending gains a step after MainWP's reconnect: the dashboard is pointed at each other administrator on record and synced, and once one connects, the care account is made again and the dashboard is pointed at it.
- The client's form says that we connect the site, create one administrator account for care whose name begins with "wpcare", and delete the login they gave, and that the account stays when care ends. Where Wordfence runs, its "created outside of WordPress" alert is named once. Without a Care Account Email the module's page warns that no care account is made on clients' sites.
- A site that was Failed after a password attempt and is found connected on the dashboard no longer keeps the login typed.
- A stored login could not be read back on WHMCS, because WHMCS's API changes some characters of a value before it encrypts it; a value the module encrypts is now handed over as base64 text. A value stored before this is still read.
- A connect whose request to add the site on the dashboard is not answered in time now asks the dashboard whether it holds the site before it fails, so a site that MainWP connected slowly is no longer recorded as Failed.
- A dashboard site that another care site already records is never taken over for a second add-on of the same client at the same address.

## 0.1.0

- The module: activation creates `mod_mainwp_sites`, `mod_mainwp_tokens` and `mod_mainwp_log` and starts in dry-run mode; deactivation keeps the tables unless "Delete module data on deactivate" is ticked; a versioned, guarded upgrade routine.
- The module's page under Addons, in three tabs drawn with WHMCS's own admin classes: the care sites with what the daily check found, the settings (dashboard address, API key stored with WHMCS's encryption and never shown again, mode, care add-ons, care account email), and the log. The settings form refuses an API key that has not the form of a MainWP key.
- The care engine as plain PHP (provision, connect, suspend, resume, remove, reconcile). In dry run every command is logged with what it would do and nothing is sent.
- The dashboard client: MainWP's REST API (version 2) with the bearer key, over HTTPS only. Clients found by the WHMCS client number in their note ("WHMCS client N") and created; sites listed, read, added under a client, synced, suspended, resumed and removed. Every dashboard call is logged with its target and outcome, never the key or a password.
- "Test connection": the dashboard's client and site counts, or why it could not answer.
- Provisioning when paid: a care add-on that is Active on an Active hosting service with no unpaid invoice gets its WHMCS client found or created on the dashboard and its care site recorded as Provisioned at the service's domain. A dashboard client is never deleted.
- The client's panel on the service page, and a staff panel on the admin service page.
- Connecting a site with an administrator username and password, from the client's page or by staff, and by a key the client approves on their own site. A failure ends in Failed with a plain-words reason and is retried by the daily check.
- Suspending, resuming and removing the site as WHMCS's events say, for the care add-on and for its hosting service.
- The daily check at the end of WHMCS's daily cron, with an email to staff when something is new: it provisions, retries, mends and takes over, and reports every other mismatch without correcting it.
